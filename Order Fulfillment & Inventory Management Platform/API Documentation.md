# API Reference

This document describes the HTTP API currently implemented by the Order Fulfillment & Inventory Management Platform. The live OpenAPI schema at `/openapi.json` and Swagger UI at `/docs` are generated by FastAPI and are the definitive source for the running version.

## Base URL and conventions

- Local development base URL: `http://127.0.0.1:8000`
- Request and response bodies use JSON unless otherwise indicated.
- Protected endpoints require `Authorization: Bearer <access_token>`.
- IDs are integer database identifiers. Timestamps are ISO 8601; provide a timezone when submitting a delivery timestamp.
- List endpoints with pagination use one-based `page` and `page_size`; the default page size is 20 and the maximum is 100 unless noted.
- Unless marked optional, request body fields are required. Partial `PUT` updates accept only the fields to change.

### Roles

| Role | Meaning |
| --- | --- |
| `admin` | Platform administrator |
| `warehouse_manager` | Staff member authorized for one or more warehouses |
| `fulfillment_agent` | Fulfillment staff authorized for one or more warehouses |
| `customer` | Customer account |

Warehouse managers and fulfillment agents can access only resources within their assigned warehouses. Customers can access only their own orders, returns, payments, and notifications. Admin-only and role-specific permissions are noted by each endpoint.

## Authentication

### `POST /auth/register`

Register a customer. Public registration does not allow choosing a privileged role.

```json
{
  "email": "customer@example.com",
  "full_name": "Avery Customer",
  "password": "a-password-with-10-or-more-characters"
}
```

Returns `201` and a user object: `id`, `email`, `full_name`, `role`, `is_active`.
Password length: 10–128 characters. Duplicate email returns `409`.

### `POST /auth/login`

```json
{
  "email": "customer@example.com",
  "password": "a-password-with-10-or-more-characters"
}
```

Returns access and refresh tokens, bearer token type, and user:

```json
{
  "access_token": "<jwt>",
  "refresh_token": "<opaque-token>",
  "token_type": "bearer",
  "user": {
    "id": 12,
    "email": "customer@example.com",
    "full_name": "Avery Customer",
    "role": "customer",
    "is_active": true
  }
}
```

Inactive accounts cannot log in. Invalid credentials and inactive accounts return `401`.

### `POST /auth/refresh`

Rotates a refresh token. The previous token is revoked; store and use the newly returned tokens.

```json
{"refresh_token": "<refresh-token>"}
```

Returns the token response shown above. Invalid, revoked, expired, or inactive-user tokens return `401`.

### `POST /auth/logout`

**Authentication required.** Revokes the user's outstanding refresh tokens and increments the access-token version.

Returns `{"message":"Logged out successfully"}`.

### `GET /auth/me`

**Authentication required.** Returns the authenticated user object.

### `POST /auth/change-password`

**Authentication required.** Changes the password, revokes outstanding refresh tokens, and invalidates existing access tokens.

```json
{"new_password":"a-new-password-with-10-or-more-characters"}
```

Returns `{"message":"Password changed successfully"}`.

## Users

All user-management endpoints require the `admin` role.

| Method and path | Description |
| --- | --- |
| `POST /users` | Create a user. Body uses `email`, `full_name`, `password` and optional `role` (default `customer`). Returns `201` and user object. |
| `GET /users?page=1&page_size=20` | List users. |
| `GET /users/{user_id}` | Get a user. |
| `PUT /users/{user_id}` | Update `email`, `full_name`, and/or `is_active`. Deactivation prevents authentication. |

## Products and categories

Product and category reads require authentication. Product/category creation and updates require `admin`.

| Method and path | Description |
| --- | --- |
| `POST /products` | Create a product. Required: `sku`, `name`, `price`; optional: `description`, `category_id`, `cost_price` (default 0), `is_active` (default true). Returns `201`. SKU is unique. |
| `GET /products?page=1&page_size=20&category_id={id}&active={true\|false}` | List/filter products. |
| `GET /products/{product_id}` | Get product. |
| `PUT /products/{product_id}` | Update any supplied product fields. Set `is_active` to `false` to deactivate or `true` to activate. Inactive products cannot be ordered. |
| `POST /categories` | Create category. Body: `name`, optional `description` (up to 500 characters). Admin only; returns `201`. |
| `GET /categories` | List categories. |
| `GET /categories/{category_id}` | Get category. |
| `PUT /categories/{category_id}` | Update `name`, `description`, and/or `is_active`. Admin only. |

Price and cost price must be non-negative. Product SKU and category name are unique.

## Warehouses and warehouse memberships

| Method and path | Permission | Description |
| --- | --- | --- |
| `POST /warehouses` | Admin | Create warehouse: `name`, `location`, optional non-negative `capacity` (default 0). Returns `201`. |
| `GET /warehouses` | Authenticated | Admin sees all warehouses; other roles see only warehouses they belong to. |
| `GET /warehouses/{warehouse_id}` | Authenticated | Get warehouse if authorized. |
| `PUT /warehouses/{warehouse_id}` | Admin or assigned warehouse manager | Update supplied `name`, `location`, `capacity`, and/or `is_active`. |
| `GET /warehouses/{warehouse_id}/users` | Admin | List assigned warehouse managers and fulfillment agents. |
| `POST /warehouses/{warehouse_id}/users` | Admin | Assign a user: `{"user_id": 7}`. User must be active and have role `warehouse_manager` or `fulfillment_agent`. Returns `201`. |
| `DELETE /warehouses/{warehouse_id}/users/{user_id}` | Admin | Remove a user from the warehouse. Returns the removed user's public record. |

Warehouse names are unique. Deactivating a warehouse prevents new orders from selecting it.

## Inventory

Warehouse managers and admins can make inventory changes. Admins, warehouse managers, and fulfillment agents can read inventory, scoped to authorized warehouses for non-admins.

| Method and path | Description |
| --- | --- |
| `GET /inventory?page=1&page_size=20&warehouse_id={id}&product_id={id}&low_stock={bool}&out_of_stock={bool}` | List/filter inventory balances. |
| `GET /inventory/{product_id}?warehouse_id={id}` | Get product inventory. Without `warehouse_id`, returns the authorized warehouse balances. |
| `GET /inventory/low-stock` | List balances where `available_quantity <= reorder_level`. |
| `GET /inventory/out-of-stock` | List balances where `available_quantity == 0`. |
| `POST /inventory/adjust` | Adjust stock; manager/admin only. |
| `POST /inventory/transfer` | Transfer stock; manager/admin only. |
| `GET /inventory/transactions?page=1&page_size=20&warehouse_id={id}&product_id={id}` | Read the immutable movement ledger. |
| `GET /inventory/transactions/{transaction_id}` | Read one ledger transaction. |

Adjustment body:

```json
{
  "product_id": 3,
  "warehouse_id": 2,
  "adjustment": 25,
  "reason": "Received supplier delivery",
  "reorder_level": 5
}
```

`adjustment` is a signed integer. Positive values add available stock; negative values reduce it and cannot reduce available stock below zero. `reorder_level` is optional and non-negative. A positive adjustment can initialize a missing product/warehouse balance.

Transfer body:

```json
{
  "product_id": 3,
  "source_warehouse_id": 2,
  "destination_warehouse_id": 4,
  "quantity": 6,
  "reason": "Rebalance"
}
```

Quantity must be positive, warehouses must differ, and the acting user must be authorized for the relevant warehouses. The operation updates both balances and writes transfer-out and transfer-in ledger rows atomically.

Both inventory mutation endpoints accept an optional `Idempotency-Key` header. Responses include resulting quantities and transaction identifiers. Inventory quantities cannot be negative; there is at most one balance per product and warehouse. Every stock movement is recorded in the transaction ledger. The ledger is read-only through the API.

## Orders

### `POST /orders`

**Customer only.** Place an order; the server chooses an active warehouse with sufficient inventory for all requested items. If multiple warehouses qualify, the current implementation chooses the eligible warehouse with the lowest ID. Inactive products cannot be ordered.

```json
{
  "items": [
    {"product_id": 3, "quantity": 2, "discount": "1.00"},
    {"product_id": 8, "quantity": 1}
  ]
}
```

`items` must contain at least one line. Each line requires a positive integer `quantity` and `product_id`; `discount` is optional, non-negative, and cannot exceed that line's subtotal. Unknown fields (including client-supplied warehouse, tax, or expected-delivery values) are rejected. Order creation reserves stock in the same database transaction. `Idempotency-Key` is optional.

The expected delivery estimate is five calendar days from order placement. Prices and tax are snapshotted per line. Initial tax rate is 0%; configured tax is calculated after discount and rounded to two decimal places.

### Order read, list, update, and assignment routes

| Method and path | Permission | Description |
| --- | --- | --- |
| `GET /orders?page=1&page_size=20` | Authenticated | Customers see their own orders; warehouse roles see authorized warehouses; admins see all. |
| `GET /orders/{order_id}` | Authenticated | Get an authorized order. |
| `GET /orders/{order_id}/items` | Authenticated | Get order lines and price/tax snapshots. |
| `GET /orders/{order_id}/history` | Authenticated | Get status history for an authorized order. |
| `POST /orders/{order_id}/cancel` | Customer (own order) or authorized staff | Cancel only where the state machine permits. Reservations are released atomically. |
| `PUT /orders/{order_id}` | Admin, assigned warehouse manager, or fulfillment agent | Change status and/or expected delivery date. |
| `POST /orders/{order_id}/assign` | Admin or assigned warehouse manager | Assign an active agent authorized for the order's warehouse. Body: `{"agent_id": 9}`. |
| `POST /orders/{order_id}/reassign` | Admin or assigned warehouse manager | Add a new current assignment; assignment is audited and notifies the agent. Same body as assign. |

Order list filters: `status`, `customer_id`, `warehouse_id`, `payment_status`,
`created_from`, `created_to`, `min_total`, `max_total`. Sorting parameters:
`sort_by` (`created_at`, `total_amount`, or `status`) and `sort_order` (`asc`
or `desc`). Pagination is one-based, page size 1–100.

`PUT /orders/{order_id}` accepts a partial body:

```json
{"status":"processing"}
```

or:

```json
{"expected_delivery_at":"2026-10-20T15:00:00Z"}
```

The delivery timestamp must be timezone-aware and in the future. Changes are audited; delivery-date changes notify the customer. Invalid state transitions return `409`.

### Fulfillment routes

Warehouse staff can view pending orders in authorized warehouses. Agents can process only orders currently assigned to them and within their warehouse scope.

| Method and path | Resulting status |
| --- | --- |
| `GET /fulfillment/orders/pending` | List pending orders in scope. |
| `GET /fulfillment/orders/assigned-to-me` | Fulfillment agent only; list current assignments. |
| `POST /fulfillment/orders/{order_id}/accept` | `confirmed` |
| `POST /fulfillment/orders/{order_id}/start-processing` | `processing` |
| `POST /fulfillment/orders/{order_id}/pack` | `packed` |
| `POST /fulfillment/orders/{order_id}/ship` | `shipped`; consumes reserved stock. |
| `POST /fulfillment/orders/{order_id}/deliver` | `delivered` |
| `POST /fulfillment/orders/{order_id}/fail` | `failed`; releases reservations where applicable. |

Normal progression is `pending -> confirmed -> processing -> packed -> shipped -> delivered`. Customer cancellation is allowed only while pending or confirmed. A failed or cancelled order cannot transition further.

## Payments

| Method and path | Description |
| --- | --- |
| `POST /payments/{order_id}/confirm` | Customer (own order) or admin confirms local demo payment. Optional `Idempotency-Key` header (1–200 characters); when omitted, a stable per-order key is generated. |
| `GET /payments/{order_id}` | Customer (own order), authorized staff, or admin reads payment status. |

Confirmation returns `order_id`, `payment_status`, and `provider: "local_demo"`. This is simulated payment state only; it does not contact a payment processor or transfer money.

## Returns

Customers may request returns for their shipped or delivered orders.

### `POST /returns`

```json
{
  "order_id": 42,
  "reason": "Item not needed",
  "items": [
    {"order_item_id": 105, "quantity": 1}
  ]
}
```

Each `order_item_id` must belong to the specified order. Requested quantities, including non-rejected existing returns, cannot exceed purchased quantities. Returns start in `requested`; response is `201`.

| Method and path | Description |
| --- | --- |
| `GET /returns?page=1&page_size=20&status=requested` | List returns visible to the caller, optionally filtered by status. |
| `GET /returns/{return_id}` | Get authorized return and its lines. |
| `GET /returns/{return_id}/items` | Get return lines. |
| `POST /returns/{return_id}/approve` | Admin or assigned warehouse manager: `requested -> approved`. |
| `POST /returns/{return_id}/reject` | Admin or assigned warehouse manager: `requested -> rejected`. |
| `POST /returns/{return_id}/receive` | Admin or assigned warehouse manager: `approved -> received`; returned items are added back into inventory. |
| `POST /returns/{return_id}/refund` | Admin or assigned warehouse manager: `received -> refunded`; if the order was paid, its payment status becomes `refunded`. This is not a real money transfer. |

Transitions outside this sequence return `409 INVALID_RETURN_STATUS`.

## Notifications, dashboards, audit, and tax

### Notifications

All authenticated users can access only their own notifications.

| Method and path | Description |
| --- | --- |
| `GET /notifications?unread_only=false&page=1&page_size=20` | List notifications; filter to unread with `unread_only=true`. |
| `GET /notifications/{notification_id}` | Get one notification. |
| `PATCH /notifications/{notification_id}/read` | Mark one notification read. |
| `PATCH /notifications/read-all` | Mark all caller notifications read; returns `{"updated": <count>}`. |

Examples of event types include `low_stock`, `out_of_stock`, `stock_restored`,
`order_created`, `order_cancelled`, `order_assigned`, and return/payment events.
Stock notifications are delivered in-app to warehouse managers when available
stock crosses a threshold.

### Dashboards

| Method and path | Role | Description |
| --- | --- | --- |
| `GET /dashboard/admin` | Admin | Platform order, revenue, and stock counts. |
| `GET /dashboard/warehouse?warehouse_id={id}` | Admin or assigned warehouse manager | Warehouse inventory, fulfillment, low-stock, and shipment counts. |
| `GET /dashboard/customer` | Customer | Own order counts and paid spending. |

### Audit logs

Admin only:

- `GET /audit-logs?page=1&page_size=50&action={action}&entity={entity}`
- `GET /audit-logs/{audit_id}`

Audit records are generated by relevant business operations and are not editable through the API.

### Tax configuration

- `GET /settings/tax-rate` — Any authenticated user reads `{"rate_percent": 0.00}`.
- `PUT /settings/tax-rate` — Admin only; body `{"rate_percent": 8.25}`. Rate is from 0 to 100 with up to two decimal places.

The selected rate and calculated tax are stored on order lines so existing orders retain their original totals.

## Idempotency, consistency, and concurrency

Order creation, inventory adjustment, inventory transfer, and payment confirmation accept idempotency keys where indicated. Keys are scoped to a user and endpoint; reusing a key with a different request returns a conflict. Order creation permits omission of its key. Inventory adjustments and transfers replay a stored response when a matching key is reused. Payment confirmation without a supplied key uses a stable generated key for that order. If two first-time order requests with the same key arrive concurrently, the unique database constraint can make one return `409`; a later retry with that key will find and return the committed order.

Order creation reserves inventory using a conditional database update inside the order transaction. Concurrent PostgreSQL requests cannot reserve the same units; when stock is insufficient the operation fails without committing a partial order. Inventory quantities have database non-negative checks, and a unique constraint permits only one inventory row per product/warehouse pair. Inventory changes, corresponding ledger entries, and order status effects are committed transactionally. PostgreSQL row-level locking is required for the concurrency behavior; SQLite is used for fast tests, not as a proof of PostgreSQL locking.

## Errors

Domain and HTTP errors use this envelope:

```json
{
  "success": false,
  "error": {
    "code": "INSUFFICIENT_INVENTORY",
    "message": "No active warehouse has enough available stock for all items in this order"
  }
}
```

Validation errors return HTTP `422` with code `VALIDATION_ERROR` and a `details` array. Common statuses:

| HTTP status | Typical meaning |
| --- | --- |
| `401` | Missing/invalid/expired authentication or invalid credentials |
| `403` | Caller role is not permitted to perform the operation |
| `404` | Resource does not exist or is outside the caller's visibility |
| `409` | Business-state conflict, duplicate key/data, or insufficient stock |
| `422` | Invalid request fields or unsupported operation parameters |
| `500` | Unexpected server error; response hides internal exception details |

## Example end-to-end order

1. `POST /auth/login` with customer credentials; save `access_token`.
2. `POST /orders` with `Authorization: Bearer <access_token>` and an `items` body.
3. Read order details with `GET /orders/{order_id}`.
4. Confirm local demo payment with `POST /payments/{order_id}/confirm` (optional `Idempotency-Key`).
5. Warehouse staff or the assigned fulfillment agent progresses the order using the fulfillment endpoints.
6. After delivery, request a return with `POST /returns`, then authorized warehouse staff/admin advances it through approval, receipt, and demo refund.
